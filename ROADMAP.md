# Roadmap

This document tracks the principal research and engineering directions planned for
EquilibriumPropagation.jl. The current package focuses on classical equilibrium
propagation for conservative energy-based models, using explicit Euler relaxation.

## Model construction

### Convenient continuous Hopfield network builders

**Status:** initial implementation complete. `ContinuousHopfield` constructs ordinary
`EPModel` values with hard-clamped inputs, named parameter trees, dense and optional
recurrent symmetric couplings, configurable callables and initializers, shape
validation, and vector/batched execution. The spiral and MNIST examples use this API.

Provide compositional utilities for constructing continuous Hopfield networks without
requiring users to manually flatten parameters and write the complete scalar energy.
The API should remain compatible with custom models and should make the following
pieces independently configurable:

- layer sizes and dynamical-state layout;
- neuron potential and activation functions;
- symmetric inter-layer and recurrent couplings;
- bias terms and parameter initialization;
- hard-clamped external inputs;
- supervised output costs; and
- parameter packing and unpacking.

These utilities should construct ordinary `EPModel` values so that the resulting
networks continue to work with the same solvers, differentiation backends, protocols,
and diagnostics as hand-written models.

#### Proposed constructor

The public API should use a declarative network specification followed by explicit
parameter initialization:

```julia
network = ContinuousHopfield(
    (784, 128, 10);
    activation=tanh,
    potential=QuadraticPotential(),
    input_clamp=HardClamp(),
    output_cost=BipolarSquaredError(),
    bias=true,
    recurrent=false,
)

model, parameters = setup(rng, network)
problem = EPProblem(model, parameters, NamedTuple(), images, targets)
```

`ContinuousHopfield` is a model specification, not a second model interface. Calling
`setup` returns a normal `EPModel` and its initialized parameter tree. Consequently,
all existing functions such as `equilibrate`, `solve_phases`, `ep_gradient`,
`train_step!`, and `predict` continue to operate without Hopfield-specific methods.

The layer-size tuple includes the input and output widths. With
`ContinuousHopfield((784, 128, 10))`, the input has 784 features, the dynamical state
has one 128-neuron hidden layer and one 10-neuron output layer, and `readout` returns
the output layer. Batched values use the convention `features × batch` or
`neurons × batch`.

`HardClamp()` keeps the input outside the dynamical state and passes it to the energy
as the fixed `EPProblem.input`. A later `SoftClamp(strength)` option may include an
input-state layer and add a finite penalty attracting it to the supplied input. The
initial implementation should support `HardClamp()` first.

The initialized parameters should be a named tree rather than a manually indexed flat
vector:

```julia
parameters = (
    weights=(W_input_hidden, W_hidden_output),
    biases=(b_hidden, b_output),
    recurrent=(),
)
```

For adjacent dynamical layers, one trainable matrix represents a symmetric coupling:
the forward and backward state dynamics must both be derived from the same scalar
energy term. `recurrent=false` omits within-layer couplings. With `recurrent=true`,
each dynamical layer receives a trainable symmetric zero-diagonal recurrent matrix;
the implementation should parameterize or symmetrize it in the energy rather than
allowing symmetry to drift during optimization.

The default energy generated by the constructor should have the form

```math
E(s, x; \theta) =
\sum_l \sum_i \Phi_l(s_{l,i})
- \sum_l \rho_l(s_l)^\mathsf{T} W_l\rho_{l-1}(s_{l-1})
- \sum_l b_l^\mathsf{T}\rho_l(s_l)
- E_{\mathrm{recurrent}},
```

where the hard-clamped input is `s₀ = x`, `Φ` is the neuron potential, and `ρ` is the
activation. Energy and supervised cost must be reduced as batch means, matching the
package's solver and diagnostic conventions.

The first implementation should provide:

- `QuadraticPotential()` and `tanh` defaults;
- `HardClamp()`;
- `BipolarSquaredError()` applied only to the output layer;
- dense adjacent-layer couplings;
- optional symmetric recurrent couplings;
- zero-state and user-provided state initializers; and
- Glorot-style weight initialization with user-overridable initializer functions.

Custom activations, potentials, initializers, and output costs should be callable
objects, keeping the constructor extensible without an inheritance hierarchy. Invalid
layer sizes, incompatible input or target shapes, and unsupported recurrent settings
should fail at construction or problem setup rather than during relaxation.

## Training methods

### Continuous EP

**Status:** initial implementation complete. `ContinuousEP` alternates explicit state
steps with telescoping local parameter-gradient updates, supports nudging and learning
schedules, provides optimizer-neutral and Optimisers.jl entry points, and records
state residual and parameter-motion diagnostics with joint stopping criteria.

Add continuous equilibrium propagation, with small continuous parameter updates
performed during the nudging phase instead of separating equilibrium solving and a
single parameter update into strictly distinct operations.

The design will need to specify:

- the coupled state and parameter dynamics;
- learning-rate and nudging schedules;
- stopping and stability criteria;
- optimizer integration; and
- diagnostics for both state convergence and parameter motion.

### AsymEP and Dyadic EP

**Status:** initial implementation complete. `DynamicalModel` gives arbitrary vector
fields an explicit interface separate from conservative `EPModel`. `AsymEP` implements
the frozen antisymmetric-Jacobian correction with opposite nudging, while `DyadicEP`
implements the doubled midpoint/difference dynamics. Both support array-valued states,
fixed-step `Relaxation`, parameter trees, shared diagnostics, `ep_gradient`, and the
Optimisers.jl training entry point. Tree-valued states and optional SciML solvers remain
future extensions.

Add AsymEP and Dyadic EP to support training arbitrary non-conservative dynamical
systems. An important special case is the ability to train feedforward networks,
without requiring their dynamics to derive from a scalar energy or their forward and
backward weights to be symmetric.

These methods should share as much of the existing phase, solver, differentiation,
and diagnostic infrastructure as possible while making the conservative assumptions
of classical EP explicit rather than implicit.

### Holomorphic EP

**Status:** initial implementation complete. `HolomorphicEP` samples finite-amplitude
complex nudges on a circle, relaxes complex equilibria with holomorphic state
derivatives, and extracts the first Fourier coefficient of the phase parameter
derivatives. It supports real array or tuple/named-tuple parameter trees, exposes
imaginary-leakage and convergence diagnostics, and makes the model's holomorphicity a
documented contract. The built-in quadratic Hopfield potential, squared output cost,
and recurrent symmetrization avoid conjugating active complex states.

Add Holomorphic EP as a standard conservative EP protocol for reducing the
finite-nudging bias without requiring the teaching radius to vanish. The public API
must make its stronger assumptions explicit: the augmented energy and selected
equilibrium branch must be holomorphic throughout a stable complex neighbourhood.
Complex conjugation, absolute values, clipping, ReLU-like activations, and other
non-holomorphic operations are invalid on active state values.

## Ecosystem extensions

### Lux extension

**Status:** initial implementation complete. The optional Lux extension provides
`lux_setup`, `lux_energy_model`, and `lux_dynamical_model`. Lux parameters remain the
trainable parameter tree, Lux state is converted to test mode and required to remain
unchanged during relaxation, and caller-supplied input/output maps define the boundary
between ordinary Lux evaluation and the EP dynamical state. Focused coverage exercises
Continuous EP, AsymEP, Dyadic EP, Holomorphic EP, Optimisers, test-mode BatchNorm, and
rejection of state-changing layers.

Add a Lux.jl extension, particularly for Continuous EP, AsymEP, and Dyadic EP. The
extension should allow Lux models, parameters, and model state to participate in the
new training methods while preserving Lux's explicit parameter and state conventions.

The extension should define a clear boundary between:

- ordinary feedforward Lux evaluation;
- dynamical state evolved by an EP method;
- trainable parameters;
- non-trainable model state; and
- method-specific feedback or auxiliary parameters.

### Reactant extension and minimal batching

Add a Reactant.jl extension so that supported phase solving and training workloads can
be compiled. Introduce only the minimal batching abstraction required to express and
compile minibatched examples, avoiding a package-wide data-loading or training-loop
framework.

The core execution path should avoid dynamic behavior that prevents compilation and
should make batch reduction conventions explicit for energies, costs, residuals, and
diagnostics.

## Equilibrium solvers

### Relaxation beyond explicit Euler

**Status:** initial optional integrations complete. `ODERelaxation`,
`SteadyStateRelaxation`, and `RootRelaxation` integrate Tsit5, Rodas5P, DynamicSS, and
NonlinearSolve algorithms through package extensions while preserving phase warm
starts and `EquilibriumSolution` reporting.

Add better relaxation algorithms beyond the current fixed-step explicit Euler method.
Priority directions are:

- optimized ODE integration with adaptive step sizes;
- dedicated steady-state and nonlinear root-finding methods;
- robust convergence and failure reporting;
- phase-specific solver selection and warm starts; and
- compatibility with automatic differentiation and compiled execution.

Solver-independent behavior should remain expressed through the existing equilibrium
solution and phase interfaces, allowing users to compare relaxation methods without
rewriting their models or training code.

#### Proposed algorithms

The first solver-facing API should expose package-owned algorithm wrappers while
accepting the underlying SciML algorithm explicitly:

```julia
ODERelaxation(Tsit5(); tspan=(0.0, 100.0), abstol=1e-6, reltol=1e-4)
ODERelaxation(Rodas5P(); tspan=(0.0, 100.0), abstol=1e-7, reltol=1e-5)
SteadyStateRelaxation(Rodas5P(); abstol=1e-7, reltol=1e-5)
RootRelaxation(TrustRegion(); abstol=1e-7, reltol=1e-5)
```

Names are provisional, but the separation is intentional:

- `ODERelaxation` integrates `ds/dt = -∂E/∂s` and stops at the requested horizon or
  when the state-gradient residual reaches the convergence tolerance;
- `SteadyStateRelaxation` dynamically integrates until the derivative is sufficiently
  close to zero; and
- `RootRelaxation` directly solves `∂E/∂s = 0`, using the free equilibrium as the
  initial guess for nudged phases.

All wrappers must return `EquilibriumSolution`, translate SciML return codes into the
existing `converged` flag, retain solver-specific information in an optional detail
field or accessor, and preserve phase warm starts. The first implementation may
support array-valued states only; tree-valued states need an explicit flatten/rebuild
adapter before being advertised.

#### Dependencies and extensions

The optimized solvers should be optional integrations rather than mandatory core
dependencies. Use Julia package extensions and the following SciML packages:

- [`SciMLBase.jl`](https://docs.sciml.ai/SciMLBase/stable/) for `ODEProblem`,
  `SteadyStateProblem`, common `solve` semantics, solution return codes, and problem
  remaking. This is the interface layer and does not itself provide numerical solvers.
- [`OrdinaryDiffEqTsit5.jl`](https://docs.sciml.ai/OrdinaryDiffEq/stable/) for
  `Tsit5()`, the initial adaptive non-stiff default. This is preferable to depending
  on the full DifferentialEquations.jl umbrella package.
- [`OrdinaryDiffEqRosenbrock.jl`](https://docs.sciml.ai/OrdinaryDiffEq/stable/massmatrixdae/Rosenbrock/)
  for `Rodas5P()`, the initial stiff default when gradient-flow dynamics are poorly
  conditioned.
- [`SteadyStateDiffEq.jl`](https://docs.sciml.ai/DiffEqDocs/stable/solvers/steady_state_solve/)
  for `DynamicSS`, which integrates an ODE until its derivative satisfies steady-state
  tolerances. Do not build new code around `SSRootfind`; the current SciML
  documentation directs direct root finding to NonlinearSolve instead.
- [`NonlinearSolve.jl`](https://docs.sciml.ai/NonlinearSolve/stable/basics/nonlinear_problem/)
  for `NonlinearProblem` and direct solutions of the equilibrium equation. Start with
  a robust trust-region or nonlinear polyalgorithm and permit users to supply another
  NonlinearSolve algorithm.

Suggested extension boundaries are:

```toml
[weakdeps]
SciMLBase = "0bca4576-84f4-4d90-8ffe-ffa030f20462"
OrdinaryDiffEqTsit5 = "b1df2697-797e-41e3-8120-5422d3b24e4a"
OrdinaryDiffEqRosenbrock = "43230ef6-c299-4910-a778-202eb28ce4ce"
SteadyStateDiffEq = "9672c7b4-1e72-59bd-8a11-6ac3964bc41f"
NonlinearSolve = "8913a72c-1f9b-4ce2-8d82-65094dcecaec"

[extensions]
EquilibriumPropagationOrdinaryDiffEqExt = [
    "SciMLBase",
    "OrdinaryDiffEqTsit5",
]
EquilibriumPropagationOrdinaryDiffEqRosenbrockExt = [
    "SciMLBase",
    "OrdinaryDiffEqRosenbrock",
]
EquilibriumPropagationSteadyStateDiffEqExt = [
    "SciMLBase",
    "SteadyStateDiffEq",
]
EquilibriumPropagationNonlinearSolveExt = [
    "SciMLBase",
    "NonlinearSolve",
]
```

The exact extension split may be refined so that loading a stiff algorithm does not
require `OrdinaryDiffEqTsit5`. `OrdinaryDiffEqRosenbrock` should activate through its
own small extension or through a generic SciML algorithm path. Do not add
`DifferentialEquations.jl`, `ModelingToolkit.jl`, or the full SciML stack to the core
package merely to obtain these solvers.

Start with `Tsit5()` for non-stiff dynamics and benchmark `Rodas5P()` for stiff or
ill-conditioned dynamics; solver choice must remain user-overridable. Direct root
solving should be treated as complementary rather than universally superior because
it can converge to an unwanted stationary point and is more sensitive to its initial
guess.
